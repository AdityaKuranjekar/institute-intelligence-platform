2. A test photo's journey (Stage 2 view)

  1. Phone uploads the OMR photo over HTTPS. The gateway checks the login, the institute and the role.
  2. Consent gate checks that each student in the batch has valid consent for this purpose. No consent, no processing.
  3. The photo goes to object storage (encrypted). A job goes on the queue, so the app stays fast when many institutes upload after the same exam weekend.
  4. An OMR worker reads the bubbles with OpenCV. Unclear bubbles come back to the teacher for a one-tap fix.
  5. The mastery service updates question difficulty and each student's topic mastery, and writes snapshots to Postgres (row-level security on every row).
  6. The risk service routes by age and purpose: a model for academic support; plain rules for dropout and fees under 18. It writes the weekly list with reasons.
  7. The report service drafts the parent message from a numbers file, the verifier runs eight checks, and a human-written template is used if any check fails.
  8. The notifier sends it by WhatsApp. The photo is deleted after 7 days. The audit log records who saw what.

4. Design rules that stay the same at every stage

Tenant isolation

Every table has an institute id, and Postgres row-level security enforces it. Tested on PostgreSQL 16: another institute sees 0 rows.

Privacy routing

The same age- and purpose-aware router runs everywhere. Under 18: model for academic support only; plain rules for dropout and fees; no activity tracking.

Safe reports

Numbers come only from a numbers file. A verifier checks every number. A template is the fallback, so a report never depends on the AI model.

Shared data is minimal

Between institutes, only question difficulty numbers are shared. Never names, marks or risk lists.

Same API contract

The web app and phone app use the same OpenAPI contract at every stage, so moving up does not change the screens.

Open export

CSV and API export at every stage, so the institute can leave with its data.

5. Honest limits of the cloud option

The cloud changes the privacy story READ THIS

  • Slide 10 promises that raw data never leaves the institute. That is true only at Stage 0. From Stage 1 up, the data sits on our servers, so the promise becomes "isolated per institute, hosted in India, encrypted, deleted on request".
  • We stay the data processor. The institute stays the data fiduciary. A written data-processing agreement between us is needed before any hosted pilot.
  • Host in an India region. Keep audit logs for a year. Delete OMR photos after 7 days. Have a breach-notice process.
  • Cost: hosting adds cost beyond the ₹3.6 per student in the financial model. We have not priced the stages yet, so do not quote a cloud cost until the finance model is updated.
  • Nothing from Stage 1 up is built or load-tested. Treat this page as a design, not a result.
  • A hosted model needs a lawyer's view on consent for minors, as with Stage 0.
